# 지하철 워프 설계 문서

최종 갱신: 2026-11-06 (무인 작업 4차: 데이터 갱신·QA 반영·3차 결정 반영)

## 1. 개요

지하철 노선도에서 이름이 같은 역을 포탈로 간주하는 밈을 실제 그래프로 구현한다.

예: 서울 강남 → 교대 ⇢(워프) 부산 교대 → 동래

산출물 후보는 통합 다이나믹 노선도, 워프 포함 길찾기, 퍼즐·대결 게임이다.
재미용 프로젝트이며 원칙은 "작게 하나 완성하고, 매칭 룰은 설정값으로 빼서 이것저것 실험한다"이다.

## 2. 스코프 로드맵

| Phase | 범위 | 목적 |
| :- | :- | :- |
| 0 | 한국 도시철도 + 광역철도 (표준데이터 범위, `config/kr_scope.yaml` 제외분 빼고) | 파이프라인·그래프·길찾기·지도 MVP |
| 1 | + 도쿄권 (JR, 도쿄메트로, 도에이, 주요 사철), 타이베이 | 다국어·이체자 매칭 엔진 검증 |
| 2 | + 중국 주요 도시 | 간체 매칭 대량 유입 시 룰 안정성 확인 |
| 3 | 전 세계 | 영어 번역형 이름의 허브 폭발 대응 |

- 일본은 "지하철"이 아니라 도시철도 전반을 넣어야 한다. 예: 신오쿠보는 JR 야마노테선 단독역이다.
- 다음 Phase는 이전 Phase의 그래프 지표가 납득 가능할 때 진행한다.

| 한국 공식 환승 정보 (3차~) | 표준데이터 '환승역구분'·'환승노선번호' + `config/kr_transfer_codes.yaml` | 코드 체계가 섞여 있어 별칭·노선 패밀리 해석 필요 |
| 노선별 정차 순서 | OSM route relation (Overpass API) | 지선 처리 주의. ODbL. Phase 0 세션에서는 Overpass 접근 불가로 미사용 |
| 노선 순서·좌표 교차검증 (Phase 0~) | Wikidata P197(인접역)·P625(좌표) | CC0. 검증 근거로만 쓰고, 라벨은 매칭에 쓰지 않는다 |

| 일본 (Phase 1b, 5차~) | Wikidata (P81·P131·P197·P296·P625·P5817·P1448·P465) | CC0. ODPT는 4차 결정으로 미접근, 운영사·국토수치정보·Geofabrik은 3차 조사에서 막힘. ja 라벨 = native_label |
| 한자 이체자 (Phase 1 T2) | OpenCC 사전(pip `opencc`), Unihan_Variants.txt (unicode.org) | 규칙(변환 사슬·필드·클래스 상한)은 ruleset |
| 다국어 공식명 (Phase 1~) | 운영사 공식 표기 우선. Wikidata는 공식명 속성(P1448)만 고려 | Wikidata 일반 라벨은 커뮤니티 번역이라 사용 금지 (매칭 폭발 원인) |
| 중국 (Phase 2) | OSM | 공개 GTFS가 거의 없는 것으로 알려짐 (검증 못 함). 지도 서비스 크롤링 금지 |

## 4. 데이터 모델

- **Station**: id, 좌표, 운영기관, 노선 목록, names[]
- **Name**: text, lang (ko, en, zh-Hant, ja ...), script, source, official(bool), grade (4차: official / native_label / foreign_label, `config/name_grades.yaml`)
- **Line**: id, 운영기관, 정차역 순서 (지선은 별도 시퀀스로 분리)
- **RideEdge**: 같은 노선에서 인접한 두 역
- **StationCluster**: 같은 물리적 역(환승역)의 묶음
- **Portal (이름 노드)**: 정규화된 이름 하나가 노드 하나. 그 이름을 가진 클러스터들과 연결한다. 하이퍼엣지를 노드로 푼 이분 그래프 구조라서 역 k개짜리 포탈도 엣지 k개로 끝난다.

## 5. 매칭 룰 (`config/rulesets/*.yaml`)

### 5.1 정규화

- Unicode NFKC, 앞뒤 공백 제거, 가운뎃점 변형 통일 (· ‧ ・ .)
- 접미사 "역" 제거
- 괄호 부역명 제거. 예: 교대(법원·검찰청) → 교대
- 부분 일치는 어떤 등급에서도 허용하지 않는다. 예: 시청 ≠ 인천시청

### 5.2 환승 vs 워프

- 3차부터 기본 규칙은 `transfer_rule: official_first`: 정규화 이름이 같은 두 역 레코드에 대해
  - 표준데이터 공식 환승 정보가 서로를 환승노선으로 적었으면(한쪽만이라도) 같은 StationCluster(환승). 상한 `official_max_distance_m`
  - 둘 다 공식 정보가 완전한데 서로를 안 적었으면 거리와 무관하게 분리 → 포탈 후보
  - 정보가 불완전하거나 같은 노선 패밀리(직결 경계, 노선번호 분할)면 거리 D 이하일 때 묶는다
- 2차까지의 규칙(`transfer_rule: distance`): 정규화 이름이 같고 거리가 D 이하이면 묶고, 넘으면 포탈.
- 공식 정보가 없는 데이터(타이베이 등)는 자동으로 거리 D 규칙이 된다.
- 옵션 `use_parenthetical_alias`: 괄호 부역명을 환승 판정용 별칭으로 쓴다 (예: 4호선 총신대입구(이수) ↔ 7호선 이수). 포탈 매칭에는 쓰지 않는다.
- D 기본값은 500m이고 ruleset에서 조정한다. 애매한 케이스: 2호선 신촌 vs 경의선 신촌.
- 4차: 역외 환승 수동 목록(`config/kr_offsite_transfers.yaml`, ruleset `cluster.offsite_transfers`). 연결 통로 없이 역 밖으로 나와 교통카드로 갈아타는 같은 이름 쌍은 공식 정보가 '일반역'이어도 묶는다. 포탈은 "현실에서 불가능한 이동"이어야 한다는 원칙.

### 5.3 포탈 등급

| 등급 | 조건 | 기본 비용 | 도입 시점 |
| :- | :- | :- | :- |
| T1 | 같은 언어·같은 문자 공식명의 정확 일치 | 1 | Phase 0 |
| T2 | 한자 이체자 정규화 후 일치 (敎/教, 廳/庁/厅 등). OpenCC, Unihan 이체자 데이터 사용 | 2 | Phase 1 |
| T3a | 번역형 영어명 정확 일치 (City Hall, Sports Complex) | 3 | Phase 1, 4차에 분리 |
| T3b | 로마자 표기가 우연히 같은 영어명 (성남 ↔ 석남 Seongnam) | 3 | 4차에 분리, 기본 꺼짐 |

- 등급별 on/off와 비용은 ruleset에서 지정한다.
- 3차 구현(ruleset 키): 등급별 `langs`·`scripts`·`kinds`·`official_only`·`sources`(이름 출처 허용 목록), `normalize`(공통 정규화 위에 덮어쓰기: T2 '站/車站/驛' 접미사, T3 casefold·' station' 접미사), `script_check`(정규화된 이름의 글자가 선언한 문자 체계인지), T2 `variant_fold`(OpenCC 변환 사슬 → Unihan 필드 union-find, 대표 = 최소 코드포인트, 클래스 상한). `portals.dedupe_subsumed`: 더 싼 등급 포탈이 이미 같은 클러스터 집합을 잇고 있으면 비싼 등급 포탈은 만들지 않는다.
- 한국 쪽 T2 이름은 표준데이터 한자역사명, T3는 표준데이터 영문역사명 (다국어 파일의 중국어 번역명·영문명은 쓰지 않는다).
- 4차 이름 출처 등급: 이름마다 official / native_label(현지어 라벨, 준공식) / foreign_label을 기록하고, 등급별 `grades` 허용 목록과 `native_only`(그 나라 현지어 이름만)로 고른다. 기본은 official + native_label. 영어 라벨(foreign_label)은 T3a·T3b에서만 쓰고, 포탈 신뢰도(`confidence`: high/medium/low = 매칭에 쓰인 가장 낮은 등급)를 표시한다.
- 4차 T3a/T3b 판정: 정규화된 영어명에 ruleset `translation_words`의 영단어가 하나라도 있으면 번역형(T3a), 아니면 로마자형(T3b).
- 허브 차수 상한(cap) 옵션: 포탈 하나에 연결 가능한 클러스터 수를 제한한다 (Phase 3 대비).

### 5.4 비용 함수

- 승차 1역 = 1, 환승 = 0 (설정 가능), 워프 = 등급 비용
- 알고리즘: 비용이 0과 1뿐이면 0-1 BFS, 그 외에는 Dijkstra

## 6. 그래프 지표 (빌드마다 출력)

- 역 수, 승차 엣지 수, 포탈 수 (등급별)
- 연결 컴포넌트 수(약연결), 최대 컴포넌트 비율, 강연결 컴포넌트 수 (3차~, 유향 엣지 대비)
- 지름 (정확값 또는 근사값). 3차부터 순서쌍 (출발 → 도착) 기준. 유향 엣지(단방향 구간)가 있어 d(s,t) ≠ d(t,s)
- 포탈 차수 상위 20개
- 워프가 없으면 고립되는 컴포넌트 목록

룰 튜닝 기준: 지름이 지나치게 줄어들거나 특정 포탈의 차수가 튀면 룰을 조인다.

다국가 그래프 추가 지표 (Phase 1, `pipeline/17_compare_world_rulesets.py`): 등급별 국가 간 포탈 목록, 국가 간 연결 여부, 국내 우회 효과(기준 ruleset보다 국내 순서쌍 최단 비용이 줄어든 비율), 허브 폭발 판정(`config/world_compare.yaml`: T2·T3 차수 ≥ 5, 포탈 수 ×2, 같은 범위 지름 20% 감소).

## 7. 게임 모드 (백로그)

- 루트 맞추기
- 최단 루트 대결 (위키레이싱 구조). 문제 선정 지표: 워프 없는 경로 대비 단축 폭이 크고 최적해 개수가 적은 출발·도착 쌍
- N정류장 최대 거리: 오프라인 전수 계산 필요
- 데일리 챌린지 + 이모지 결과 공유 (2026-11-05 구현: `web/daily.html`, 퍼즐 후보는 `pipeline/10_build_game_data.py`)
- 포탈 등급 해금형 진행: 초반에는 T1만 열고 이후 T2·T3 해금

## 8. 시각화

- Phase 0: 지도(MapLibre 또는 Leaflet) 위 실제 좌표 + 워프 곡선 아크
- 4차부터 **도식 노선도(8방향 스키매틱)를 스코프에 넣는다** (`web/schematic.html`). 원칙:
  - 자동 생성만 한다. 공식 노선도 이미지·역 배치는 참고하지도 쓰지도 않는다. 노선 색만 쓴다.
  - 입력은 우리 그래프(클러스터 = 물리적 역, 승차 엣지)와 지리 좌표뿐이다. 권역(도시)별 패널로 나눈다: 수도권, 부산(동해선 포함), 대구, 대전, 광주, 타이베이.
  - 레이아웃 엔진: (1) LOOM(github.com/ad-freiburg/loom, GPL-3.0)을 빌드 단계에서 받아 외부 CLI로만 쓰는 안(코드 복사 금지), (2) 자체 octilinear MIP (Nöllenburg & Wolff 2011식, HiGHS). 4차 세션에서는 LOOM 받기·빌드가 막혀 (2)로 만든다.
  - 포탈 역에는 포탈 아이콘과 목적지를 붙이고, 누르면 목적지 권역 패널로 이동. 같은 권역 안 포탈(양평·동래·신촌 등)은 점선. 길찾기 경로를 도식 위에 칠하고 워프 구간은 패널 이동 단계로 보여 준다. 지리 지도 ↔ 도식 전환 토글.
- 이후 검토: 전 세계 스케일은 지구본 + 아크 레이어 (deck.gl ArcLayer)
- 배포: GitHub Pages (정적 사이트)
